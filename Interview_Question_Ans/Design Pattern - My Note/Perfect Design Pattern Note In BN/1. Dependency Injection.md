হ্যাঁ। আমরা **framework-specific syntax মুখস্থ না করে pattern-এর মূল চিন্তাটা** শিখব। তারপর একই concept Laravel, Spring Boot, Node.js/Next.js—যেকোনো জায়গায় map করতে পারবে।

নিচে **Design Pattern #1 — Dependency Injection (DI)**-এর complete note দিলাম।

# Design Pattern #1 — Dependency Injection (DI)

## 1. প্রথমে গল্প দিয়ে বুঝি

ধরো তুমি একটা **Restaurant Management System** বানাচ্ছ।

তোমার `OrderService`-এর কাজ হলো order তৈরি করা।

Order তৈরি হওয়ার সময় তাকে database-এ save করতে হবে।

তাই `OrderService`-এর দরকার:

```text
Database
```

এই "দরকার"-টাই হলো **Dependency**।

অর্থাৎ:

> `OrderService` depends on `Database`.

### Dependency মানে কী?

কোনো class/function কাজ করার জন্য অন্য কোনো object/class-এর প্রয়োজন হলে সেই প্রয়োজনীয় object-টি হলো তার **dependency**।

```text
OrderService
      ↓
   depends on
      ↓
   Database
```

---

# 2. Dependency Injection-এর সংজ্ঞা

### সহজ সংজ্ঞা

> **Dependency Injection হলো এমন একটি technique যেখানে কোনো object তার প্রয়োজনীয় dependency নিজে তৈরি না করে বাইরে থেকে গ্রহণ করে।**

তিনটি শব্দ মনে রাখো:

```text
Dependency
    +
Injection
    =
Dependency Injection
```

### Dependency

যেটা আমার দরকার।

### Injection

সেটা বাইরে থেকে আমার মধ্যে ঢুকিয়ে দেওয়া।

---

# 3. DI না থাকলে সমস্যা কী?

প্রথমে traditional code দেখি।

```text
OrderService
     │
     └── নিজেই Database তৈরি করছে
```

Pseudo code:

```text
CLASS OrderService

    database = NEW Database()

    FUNCTION createOrder()
        database.save(order)
    END

END
```

এখানে `OrderService` নিজেই বলছে:

```text
আমি Database বানাবো।
```

এটাই problem।

---

# 4. কেন এটা খারাপ?

ধরো আজ তুমি MySQL ব্যবহার করছ।

```text
OrderService
      ↓
    MySQL
```

কিন্তু কাল PostgreSQL ব্যবহার করতে চাও।

তাহলে `OrderService` পরিবর্তন করতে হবে।

আবার testing-এর সময় real database ব্যবহার না করে fake database ব্যবহার করতে চাইলে?

আবার `OrderService` পরিবর্তন করতে হবে।

অর্থাৎ:

```text
OrderService
     ↓
 tightly coupled
     ↓
 MySQL Database
```

এটাকে বলে **Tight Coupling**।

---

# 5. DI ব্যবহার করলে কী হবে?

এবার আমরা বলব:

```text
OrderService
     ↓
"আমার Database দরকার"
```

কিন্তু:

```text
OrderService
     X
Database তৈরি করবে না
```

বরং বাইরে থেকে Database দেওয়া হবে।

```text
Database
    ↓
    ↓ inject
    ↓
OrderService
```

---

# 6. প্রথম DI Pseudocode

```text
CLASS OrderService

    FUNCTION constructor(database)

        THIS.database = database

    END


    FUNCTION createOrder(order)

        THIS.database.save(order)

    END

END
```

এখানে `database` কোথা থেকে আসছে?

বাইরে থেকে।

---

# 7. Dependency কোথায়?

এখানে:

```text
constructor(database)
```

`database` হলো dependency।

কারণ:

```text
OrderService
    needs
Database
```

---

# 8. Injection কোথায়?

এখন বাইরে থেকে:

```text
database = NEW Database()

orderService =
    NEW OrderService(database)
```

এখানে:

```text
NEW OrderService(database)
```

এর মাধ্যমে Database ঢুকিয়ে দেওয়া হচ্ছে।

এটাই **Injection**।

---

# 9. পুরো Flow

```text
                 Application
                     │
                     │ creates
                     ↓
                 Database
                     │
                     │ inject
                     ↓
               OrderService
                     │
                     ↓
                 createOrder()
```

মনে রাখবে:

```text
Dependency = কী দরকার?

Injection = সেটা কীভাবে দেওয়া হচ্ছে?
```

---

# 10. এখন একটু বাস্তব Code

Raw JavaScript দিয়ে করি।

### Database

```js
class Database {

    save(order) {
        console.log("Order saved");
    }
}
```

### OrderService

```js
class OrderService {

    constructor(database) {
        this.database = database;
    }

    createOrder(order) {
        this.database.save(order);
    }
}
```

### Application

```js
const database = new Database();

const orderService =
    new OrderService(database);

orderService.createOrder({
    product: "Laptop"
});
```

এখানে সবচেয়ে গুরুত্বপূর্ণ line:

```js
new OrderService(database);
```

এখানে আমরা `database` inject করছি।

---

# 11. DI-এর মূল Rule

এই rule-টা মাথায় বসিয়ে ফেলো:

> **A class should receive what it needs instead of creating what it needs.**

বাংলায়:

> **যা দরকার সেটা নিজে তৈরি না করে বাইরে থেকে নাও।**

---

# 12. এবার গল্পে নতুন সমস্যা

ধরো তোমার company বলল:

> "আমরা MySQL বাদ দিয়ে PostgreSQL ব্যবহার করব।"

আমাদের প্রথম code হলে:

```text
OrderService
      ↓
new MySQLDatabase()
```

Problem।

কিন্তু DI architecture হলে:

```text
                 OrderService
                      ↑
                      │
              Database dependency
                      ↑
              ┌───────┴────────┐
              │                │
           MySQL           PostgreSQL
```

OrderService-এর কোনো পরিবর্তন লাগবে না।

---

# 13. Pseudocode

```text
CLASS MySQLDatabase

    FUNCTION save(order)
        SAVE order into MySQL
    END

END
```

```text
CLASS PostgreSQLDatabase

    FUNCTION save(order)
        SAVE order into PostgreSQL
    END

END
```

Service:

```text
CLASS OrderService

    FUNCTION constructor(database)

        THIS.database = database

    END

    FUNCTION createOrder(order)

        THIS.database.save(order)

    END

END
```

MySQL ব্যবহার:

```text
database = NEW MySQLDatabase()

service = NEW OrderService(database)
```

PostgreSQL ব্যবহার:

```text
database = NEW PostgreSQLDatabase()

service = NEW OrderService(database)
```

`OrderService` অপরিবর্তিত।

এটাই DI-এর শক্তি।

---

# 14. এখান থেকে Loose Coupling

আগে:

```text
OrderService
      ↓
MySQL
```

এখন:

```text
OrderService
      ↓
Database
      ↑
      │
 ┌────┴────┐
 ↓         ↓
MySQL   PostgreSQL
```

এখন `OrderService` নির্দিষ্ট database-এর ওপর tightly coupled নয়।

এটাকে বলে:

> **Loose Coupling**

---

# 15. কিন্তু এখানে একটা গুরুত্বপূর্ণ সমস্যা আছে

Raw JavaScript-এ আমরা লিখলাম:

```js
constructor(database) {
    this.database = database;
}
```

কিন্তু `database` আসলে কী?

```text
MySQLDatabase?
PostgreSQLDatabase?
MongoDatabase?
FakeDatabase?
```

আমাদের একটা **contract** দরকার।

এখানেই আসে **Abstraction**।

Conceptually:

```text
Database
   ↑
   │
 ┌─┴─────────────┐
 │               │
MySQL         PostgreSQL
```

`OrderService` বলবে:

> আমার concrete MySQL class দরকার নেই।
> আমার শুধু এমন একটা Database দরকার যার `save()` method আছে।

---

# 16. Pseudocode-এ Contract

```text
INTERFACE Database

    FUNCTION save(order)

END
```

তারপর:

```text
CLASS MySQLDatabase IMPLEMENTS Database

    FUNCTION save(order)
        ...
    END

END
```

```text
CLASS PostgreSQLDatabase IMPLEMENTS Database

    FUNCTION save(order)
        ...
    END

END
```

Service:

```text
CLASS OrderService

    FUNCTION constructor(database: Database)

        THIS.database = database

    END

END
```

এখানে `OrderService` এখন জানে না:

```text
MySQL
PostgreSQL
MongoDB
```

সে শুধু জানে:

```text
Database
```

---

# 17. এটিই আসলে Dependency Inversion-এর দিকে যাচ্ছে

Architecture:

```text
OrderService
      ↓
 Database Abstraction
      ↑
 ┌────┴───────┐
 │            │
MySQL      PostgreSQL
```

এটা অনেক গুরুত্বপূর্ণ backend architecture।

DI এবং Dependency Inversion এক জিনিস নয়, কিন্তু DI ব্যবহার করে Dependency Inversion Principle বাস্তবায়ন করা সহজ হয়।

---

# 18. এখন Controller → Service → Repository

এবার এটাকে backend application-এর মতো করি।

```text
Request
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

### Repository

```text
CLASS UserRepository

    FUNCTION findUser(id)
        return database.find(id)
    END

END
```

### Service

```text
CLASS UserService

    FUNCTION constructor(userRepository)

        THIS.userRepository = userRepository

    END

    FUNCTION getUser(id)

        return THIS.userRepository.findUser(id)

    END

END
```

### Controller

```text
CLASS UserController

    FUNCTION constructor(userService)

        THIS.userService = userService

    END

    FUNCTION show(id)

        return THIS.userService.getUser(id)

    END

END
```

---

# 19. এখন Dependency Graph

খুব গুরুত্বপূর্ণ:

```text
UserController
       │
       │ depends on
       ↓
UserService
       │
       │ depends on
       ↓
UserRepository
       │
       │ depends on
       ↓
Database
```

এখন Application startup-এ dependency তৈরি হবে:

```text
database
   ↓
UserRepository
   ↓
UserService
   ↓
UserController
```

এটাই **Dependency Composition**।

# 20. Manual DI

Framework ছাড়া আমরা নিজেরাই করতে পারি:

```js
const database =
    new Database();

const userRepository =
    new UserRepository(database);

const userService =
    new UserService(userRepository);

const userController =
    new UserController(userService);
```

এখানে কোনো magic নেই।

এটাই DI-এর আসল ভিত্তি।

---

# 21. Framework আসলে কী করে?

এখন Spring Boot/Laravel-এর magic বুঝতে পারবে।

Framework basically বলে:

```text
তুমি আমাকে বলো:

UserController কী চায়?

        ↓

UserService

UserService কী চায়?

        ↓

UserRepository

UserRepository কী চায়?

        ↓

Database

আমি এগুলো তৈরি করে
একটার মধ্যে আরেকটা inject করে দেব।
```

অর্থাৎ:

```text
                 DI Container
                      │
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
    Database      Repository      Service
        │             │             │
        └─────────────┴─────────────┘
                      ↓
                 Controller
```

---

# 22. Spring Boot-এ কী হচ্ছে?

তুমি যখন লেখো:

```java
@Service
public class UserService {

    private final UserRepository repository;

    public UserService(UserRepository repository) {
        this.repository = repository;
    }
}
```

Spring-এর container:

```text
UserService needs UserRepository
              ↓
Spring Container
              ↓
Create UserRepository
              ↓
Inject UserRepository
              ↓
UserService
```

তুমি manually:

```java
new UserRepository()
```

করছ না।

Framework করছে।

---

# 23. Laravel-এও একই concept

তুমি যদি লেখো:

```php
class UserService
{
    public function __construct(
        UserRepository $repository
    ) {
        $this->repository = $repository;
    }
}
```

Laravel Container বুঝবে:

```text
UserService
     ↓
needs UserRepository
     ↓
Container resolves UserRepository
     ↓
injects it
```

---

# 24. Next.js / Node.js-এ

Framework তোমার জন্য automatic DI না করলেও তুমি manually করতে পারো:

```js
const repository =
    new UserRepository(database);

const service =
    new UserService(repository);

const controller =
    new UserController(service);
```

অথবা নিজের DI Container বানাতে পারো।

---

# 25. DI-এর ৩টি প্রধান ধরন

একজন Backend Engineer হিসেবে অন্তত নামগুলো জানতে হবে।

### 1. Constructor Injection ⭐⭐⭐

সবচেয়ে important।

```text
CLASS UserService

    constructor(repository)
        this.repository = repository
    END

END
```

Spring Boot-এ এটিই সবচেয়ে common/recommended।

---

### 2. Setter Injection

```text
service = NEW UserService()

service.setRepository(repository)
```

অর্থাৎ dependency পরে দেওয়া হচ্ছে।

---

### 3. Method Injection

```text
service.process(repository)
```

শুধু নির্দিষ্ট method-এর জন্য dependency দরকার হলে।

---

# 26. কোনটা সবচেয়ে ভালো?

সাধারণভাবে:

```text
Constructor Injection
        ↓
       BEST
```

কারণ object তৈরি হওয়ার সময়ই তার required dependency পাওয়া যায়।

তাই object invalid state-এ থাকার সম্ভাবনা কম।

---

# 27. Testing-এ DI কেন এত গুরুত্বপূর্ণ?

ধরো `UserService` database ব্যবহার করে।

Real database:

```text
UserService
     ↓
MySQL
```

Test-এর সময় আমরা fake repository দিতে পারি:

```text
UserService
     ↓
FakeRepository
```

Pseudocode:

```text
fakeRepository = NEW FakeUserRepository()

service =
    NEW UserService(fakeRepository)

result =
    service.getUser(1)
```

Real database লাগল না।

এটাকে বলে **Testability**।

# 28. DI-এর পুরো গল্প একবার

### সমস্যা:

```text

```

### সমস্যা:


```text

    ↑

```

```text
Dependency Injection
```

```text
Loose Coupling
+
Testability
+
Maintainability
+
Replaceability
```

# 29. DI মনে রাখার সবচেয়ে সহজ Formula

```text
BAD:

Class
 ↓

GOOD:

Class
 ↓
receives dependency
```

আরও ছোট করে:

```text
DON'T CREATE
       ↓

```

# 30. Framework-independent Mental Model

যেকোনো framework-এ DI দেখলে প্রথমে এই ৪টা প্রশ্ন করবে:

```text
1. কোন class-এর dependency আছে?

2. Dependency কী?

3. Dependency কে তৈরি করছে?

4. Dependency কোথা থেকে inject হচ্ছে?
```

উদাহরণ:

```text
UserController
       ↓
needs UserService

UserService
       ↓
needs UserRepository

UserRepository
       ↓
needs Database
```

তারপর:

```text
Who creates them?
        ↓
DI Container / Application
```

এই mental model থাকলে Laravel, Spring Boot, NestJS, .NET, Django ecosystem বা অন্য framework—সবকিছুর DI বুঝতে পারবে।

```text
DEPENDENCY INJECTION
│
├── Dependency
│     └── অন্য object/class যেটা আমার দরকার
│
├── Injection
│     └── dependency বাইরে থেকে দেওয়া
│
├── Main Goal
│     └── Loose Coupling
│
├── Most Important
│     └── Constructor Injection
│
├── Benefits
│     ├── Loose Coupling
│     ├── Testability
│     ├── Maintainability
│     └── Replaceability
│
└── Architecture
      Controller
          ↓
       Service
          ↓
      Repository
          ↓
       Database
```

### সবচেয়ে গুরুত্বপূর্ণ code

```js
class UserService {

    constructor(userRepository) {
        this.userRepository = userRepository;
    }
}
```

এবং:

```js
const repository =
    new UserRepository();

    new UserService(repository);
```

**এই দুইটা code বুঝে ফেললে DI-এর core concept তুমি বুঝে ফেলেছ।**

পরের pattern **Factory Pattern**-এ একই teaching style-এ যাব: **গল্প → সমস্যা → pseudo code → simple code → DI-এর সাথে সম্পর্ক → real backend example → framework mapping → cheat sheet**।
